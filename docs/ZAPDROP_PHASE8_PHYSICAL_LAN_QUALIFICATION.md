# Zapdrop Phase 8 Physical-LAN Qualification

**Purpose:** Provide a repeatable, evidence-based procedure for validating trusted offline file and folder sharing on real Windows PCs, private Wi-Fi, routers, and phone hotspots.

This package is deliberately separate from automated Rust and frontend tests. A local loopback or scheduler test cannot prove Windows firewall behavior, Wi-Fi client isolation, multicast discovery, hotspot behavior, real throughput, or multi-PC user consent. Those observations must be performed on the target hardware and recorded in an evidence file generated by `scripts/physical_lan_qualification.sh`.

## Required operating rules

Use a private network only and keep the internet disconnected during the test window. Pair devices by comparing fingerprints out of band, and never treat discovery as authorization. Every receiver must visibly approve the incoming offer before content is written. Do not globally disable a firewall, expose a public interface, upload private files, or place private keys in the evidence directory.

The **v1 direct transfer path is the default acceptance path**. The experimental `swarm-v2` path is optional and must be run as a separate lane with its explicit environment switch recorded. Its results must not be combined with v1 results or described as TLS 1.3 or production-certified security.

## Procedure

First run the automated qualification from the repository root. Then create a dated evidence directory and form:

```bash
cd /home/ubuntu/Zapdrop
./scripts/qualification.sh
./scripts/physical_lan_qualification.sh --self-check
./scripts/physical_lan_qualification.sh --init evidence/phase8-<date>
```

Record the exact Zapdrop commit, executable or installer hash, Windows versions, device names, trusted fingerprints, network topology, scheduler settings, fixture hashes, and evidence paths. Use a controlled fixture containing a zero-byte file, a Unicode filename, nested directories, duplicate names, and a sufficiently large file to exercise progress and cancellation. Compare sender and receiver hashes after every successful transfer.

Run `LAN-01` and `LAN-02` first to establish ordinary router and hotspot behavior. Run `LAN-03` on a network where multicast is unavailable or client isolation is enabled, using the manual endpoint path and verifying that an untrusted peer cannot obtain a manifest or payload. Run `LAN-04` without broad firewall weakening. Run `SWARM-01` through `SWARM-03` with two, four, and eight trusted recipients, recording configured parallelism, queue depth, bandwidth cap, observed active sessions, child outcomes, and parent history. Exercise slow, rejected, transient-failure, and cancelled recipients separately. Finish with the safety and operations rows, preserving logs for every failure.

## Acceptance interpretation

The runner accepts four statuses: `PASS`, `FAIL`, `BLOCKED`, and `NOT_RUN`. `PASS` requires reproducible evidence and matching content hashes. `FAIL` requires the first failing step and preserved logs. `BLOCKED` identifies the unavailable hardware, permission, or environment. `NOT_RUN` is only an incomplete state and never counts as acceptance.

Use the validator after editing the evidence form:

```bash
./scripts/physical_lan_qualification.sh --validate evidence/phase8-<date>/qualification-evidence.md
```

The validator returns a non-zero status while any row is unresolved. It does not inspect the network or manufacture test results; it checks that the required matrix is present and uses valid status values.

## Matrix and remaining gate

| Area | Automated coverage | Physical evidence still required |
|---|---|---|
| Trust and safe receive | Unit and loopback tests cover trust binding, approval, path validation, and history. | Fingerprint verification, user consent, revoked trust, firewall, and malicious-peer behavior on real PCs. |
| One-to-many scheduling | Local three-recipient harness covers one active/two queued children, simulated failure, cancellation, partial parent history, and active-count cleanup. | Two, four, and eight actual recipients; mixed file/folder content; slow-peer fairness; bandwidth observations; hotspot/router behavior. |
| Offline operation | Code path does not require cloud services for payload transfer. | Internet-disconnected execution on router and hotspot networks. |
| Windows operation | Frontend build and Rust suites run in the repository environment. | Windows installation, WebView2/runtime behavior, private firewall profile, sleep/wake, interruption, resume, and clean uninstall. |
| Experimental v2 | Gated v2 test suite covers protocol structures and direct loopback behavior. | Separate packet-capture and physical-LAN review; no production-security claim before independent signoff. |

Phase 8 is not accepted as production-complete until the physical rows have real evidence. This package makes that gap visible and repeatable; it does not pretend that unavailable hardware was tested.
